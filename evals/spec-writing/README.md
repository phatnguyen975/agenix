# Spec Writing Evaluation

## Purpose and Scope

Evaluate behavioral completeness, section ownership, acceptance coverage and truthful automation readiness. This directory is development-only and independent of runtime resources.

## Execution

Use fresh contexts with only permitted raw evidence and the skill/resources. Hide rubrics and coordinator conclusions. For the save case, provide an empty disposable root and authorize only the requested spec and parent directories. Other cases are read-only. No network, Git publication, secrets, product execution or dependency installation is permitted. Model-service authority is separate from candidate tool authority.

Capture actual responses and inspect saved content. Scenario messages summarize the evaluated input contracts; do not fabricate stakeholder answers for further turns or treat a draft as approved.

## Assessment

Require all expected behaviors, no prohibited behavior and the semantic quality criterion. Programmatic assertions check exact destination/permitted file set, metadata, section structure, ID uniqueness/reference resolution and scenario-level AC identity. Semantic review assesses actual FR/rule/transition coverage, observable outcomes, section ownership, scope preservation and honest execution claims. Counting tags or checking keywords is not a semantic pass.

Separate syntax validation, semantic assessment and runtime verification. Infrastructure errors, unrun cases, uncertain judgments and failures remain distinct. Model/coordinator assessment is not human acceptance. Preserve failure dispositions rather than retrying until green.

## CI and Reproducibility

No provider, model runner or CI gate is selected. Static checks need no LLM/API key. Behavioral execution needs an inference backend; hosted inference may need credentials/costs, while local inference needs compute. Model grading adds variability.

Record candidate identity, model/settings, harness, permissions and rubric. Keep cross-model results separate and measure repeated-run variation before adopting model-based gates. Parser validation, if added later, needs an explicitly provisioned supported parser; never infer a parser pass from a regex or syntax review.

## Results and Limitations

Keep concise receipts with the reviewed change at the maintainer-selected evidence location. Retain raw material only when needed for reproduction and redact sensitive data. This procedure does not depend on temporary planning documents.

The fresh-context runs use inherited host settings rather than independently pinned model/settings. Record actual outcomes separately from scenario design. No baseline comparison, installed-host proof, renderer preview, parser execution or product-test execution is implied.
