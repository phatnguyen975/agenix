# TDD Evaluation

## Purpose and Scope

Evaluate test-first decision-making, sourced oracles, coverage boundaries, test doubles and caller composition. Development resources are independent of runtime use. Behavioral cases assess planning/advice, not autonomous product implementation.

## Files and Execution Status

| Resource                         | Role                                                            | Status                                        |

| [scenarios.json](scenarios.json) | Three inputs, semantic expectations and prohibited actions      | Model-assisted cases assessed                 |

| Structural / example checks      | Metadata, resource routes, Markdown and illustrative techniques | Maintainer checks; no per-skill static runner |

The case format is local, not an upstream harness contract. No executable runtime helper is added.

No executable line-coverage percentage applies to instructions.

## Execution

Give a fresh context one raw case input and the runtime skill path, hiding rubric, other cases and coordinator conclusions. Permit runtime-resource reads, including read-only file commands such as Get-Content. Prohibit product/test execution, writes, network, Git, secrets, installation and recursive delegation. Preserve actual response/action evidence and do not fabricate further user answers.

The separate execution walkthrough used a disposable directory with eligibility.py and test_eligibility.py, Python unittest and bytecode disabled. Contract: age 18 is eligible, age 17 is not. A None-returning stub failed the age-18 assertion; a constant True made it pass. Adding age-17 produced the next assertion failure; replacing the constant with age >= 18 made both tests pass. Refactoring review found no worthwhile additional change. No product code or user-owned artifacts were altered.

## Assessment

Require expected behaviors, no prohibited actions and semantic quality. Assess the chosen seam, independent oracle, actual versus inferred evidence, coverage limitations, preserved authority and absence of redundant approval/artifact gates. Interaction assertions must verify a contractual outward effect through the real subject; canned responses alone do not establish integration.

Structural assertions check YAML/JSON, paths/anchors and fences. Example assertions compare eight Boolean decision combinations with the minimized rules, count four valid/eight invalid state cells, and check sixteen boundary inputs against explicit independent labels. A shifted child boundary is missed by the EP representative set but detected at age 12. These checks do not prove the whole skill correct. Keep infrastructure errors, unrun checks and uncertain judgment distinct. Coordinator assessment is not human acceptance.

## CI and Reproducibility

No shared validator, provider, model runner or behavioral gate is added. Static/example checks need no LLM key. Behavioral execution requires an inference backend; hosted inference may require credentials/costs, while local inference requires compute. Pin model/settings, candidate, harness, permissions and rubric before comparing repeated runs or adopting behavioral CI gates. General static checks belong in shared infrastructure rather than a separate implementation here.
