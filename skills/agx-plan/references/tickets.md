# Plan Feature Tickets

## Inputs and Readiness

Resolve the feature on the refreshed default branch and verify the approved specification phase merged with required checks. Read the approved delivery strategy and its evidence on the feature plan branch, the feature record and pinned spec, applicable API, data and UI contracts, codebase design and test strategy. Resolve their revisions and scoped acceptance references. Check feature eligibility and dependencies under [Decide Readiness and Record Progress](../../../references/work-items-and-evidence.md#decide-readiness-and-record-progress), using [Local Tracker](../../../references/trackers/local.md#read-verify-and-update) in local mode and the applicable shared rules for Git-owned evidence in remote modes. Reconcile existing plan, tracker mappings and in-flight allocations before adding work.

## Design the Ticket Set

Determine the planning boundaries from the approved delivery strategy before splitting work. For a single scope or cross-boundary slices, plan outcomes across the corresponding approved boundary. For separate contract-coordinated tracks, identify each track's ownership, scope and contract first, then break down each track within its own boundary. Reconcile shared prerequisites and integration across the resulting ticket set.

Use [Work Breakdown Planning](../../work-breakdown-planning/SKILL.md) in `Flat` mode within each selected boundary for bounded, independently verifiable ticket outcomes. Apply its slicing, coverage, dependency and cycle checks, using Agenix records rather than its standalone template. One ticket is sufficient for a boundary if its approved outcome already fits. Across all boundaries, map the complete feature acceptance and applicable quality obligations to tickets, with no duplicated delivery obligation or unowned requirement. Preserve the approved strategy and ask about unresolved material scope or ownership.

Define only hard prerequisite edges within this feature. Explain each edge in the review; derive a valid execution order and independent parallel candidates from the DAG. Coordinate shared files and ID allocation without treating preferred scheduling as a dependency. For split delivery, define independent boundary checks and allocate real client/provider integration and required journeys to suitable tickets or a dedicated integration ticket with actual prerequisites. A mock-backed ticket has bounded acceptance; it does not establish real integration or whole-feature completion. No ticket is designated to finalize the feature.

For additions, reuse the approved strategy and definitions, allocate new IDs after all existing allocations, and identify the origin of each addition. Do not silently alter existing ticket definitions or dependencies; route required changes through amendment. Recheck the complete graph and coverage.

## Prepare Records and Publish

For each new ticket, prepare the fields in [Record Fields and Ownership](../../../references/work-items-and-evidence.md#record-fields-and-ownership): ID, title, bounded outcome, feature ID and pinned feature record, type, lowercase scope and priority, owner, dependencies, pinned scoped references and initial status. Select at least one feature acceptance ID across its references; link the relevant spec sections and applicable contract, data or UI artifacts rather than copying them. Set `READY` or `BLOCKED` from actual prerequisite evidence. Include origin when applicable. Use project-approved values or resolve material missing choices with the human. Leave task plans, task verification methods, implementation and review evidence to their owning steps.

- **Local:** render `docs/features/<feature-id>/tickets/<ticket-id>.agenix.json` using the [local ticket schema](../../../templates/records/local-ticket.schema.json); add `{id, path}` mappings to the feature record. Do not add a `tasks` array before task planning.
- **GitHub or Jira:** draft each ticket using [Native Ticket](../../../templates/records/native-ticket.md) and [Remote Tracker Records](../../../references/work-items-and-evidence.md#remote-tracker-records). Use the configured [GitHub](../../../references/trackers/github.md#create-and-read-issues) or [Jira](../../../references/trackers/jira.md#create-and-read-issues) procedure and native format. After approval, preserve the approved batch definition durably, create or reconcile tickets, read them back and add verified `{id, native-ref}` mappings to the feature record. Mirror dependencies where supported. Reconcile partial or uncertain writes before retrying; keep drafts until mappings and evidence are durable.

Verify coverage, IDs, pinned targets, ticket ownership, initial statuses, graph and tracker mappings. Run the installed [artifact validator](../../../scripts/validate-artifacts.py) with `--project-root <absolute-project-root> --stage feature-plan --item <feature-id>` where its required inputs exist. Distinguish local structural validation from remote read-back and semantic review.

Apply [Artifact Gates](../../../references/workflow-control.md#artifact-gates) to the complete definitions, graph, acceptance and integration coverage, intended Git and native writes, and evidence. Obtain approval before native creation. [Publish the Approved Candidate](../../../references/git-publication.md#publish-the-approved-candidate) on the feature plan branch, reconcile mappings and bind the approval and checks to the actual candidate. Validate again after mappings are available. Make the phase PR ready only after the complete plan and required checks are verified. Follow [Merge the Approved Head](../../../references/git-publication.md#merge-the-approved-head) and [Verify Delivery](../../../references/git-publication.md#verify-delivery-and-recover-from-a-failed-check); merge requires separate human authority. Tickets may start only after the feature plan is merged and prerequisites are met. Follow the shared session closure rules.
