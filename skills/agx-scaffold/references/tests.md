# Prepare Verification Harnesses

## Inputs and Result

Verify the merged architecture baseline and the approved scaffold structure, runtime and applicable services revisions and evidence. Read the project instructions, `config.agenix.json`, approved `docs/blueprint/test-strategy.md`, `tech-stack.md` and `codebase-design.md`. Read only applicable system, contract, data or UI foundations and conventions needed to implement the selected checks. Inspect existing tool configuration, commands, service operations and fixtures before changing them.

Deliver project-native verification harnesses and verified commands covering the approved checks across all owned release units, targets and boundaries. Preserve existing working configuration and reuse service lifecycle operations established earlier.

## Configure the Harnesses

1. Map each applicable strategy check ID to its unit, boundary, level or check type, target, run condition, selected tool, test location and dependencies. Include approved structural enforcement and architecture fitness checks from the codebase and system designs where the strategy assigns them. Cover the agreed local and later gate needs across frontend, backend and other owned units. Identify shared harnesses and real integration boundaries. Resolve missing tools, incompatible versions or materially ambiguous coverage before dependent setup.
2. Configure the selected runners, discovery, assertions, reporting and project-native test locations. Set up only the fixtures, browser targets, mocks, real dependencies and isolation controls the strategy requires. Use approved disposable services and existing reset and cleanup operations. Create only paths and files needed for these harnesses. Keep secrets out of fixtures and evidence.
3. Add representative, meaningful probes against real scaffold behavior and the relevant boundaries. Use synthetic data. Ensure checks can run before feature code exists. Do not invent business rules or represent a mock as a real integration result. Establish contract document, schema, example and runtime conformance tooling where selected, and distinguish what each validates. If a feature contract is not yet available, prove the validator with isolated valid and invalid fixtures and leave the feature-specific validation to its owning step. Exercise runtime conformance against an existing real boundary or a representative isolated fixture without claiming the future provider is implemented.
4. Verify selected tools are installed and compatible. Consult [Vitest](../../vitest/SKILL.md) only when configuring that runner, [React Testing](../../react-testing/SKILL.md) only for an applicable React component or hook harness, and [Playwright CLI](../../playwright-cli/SKILL.md) when it is the selected browser interaction tool. Follow their relevant setup guidance without adopting unrelated stacks. Use [TDD](../../tdd/SKILL.md) only for behavior-bearing probes or helpers under an approved test-first method. Use installed specification-aware validators for their selected contract formats.

## Prove and Record Readiness

For every distinct required harness, run its actual command in its intended context. Where the tool discovers tests, verify nonempty discovery and a meaningful passing probe. Demonstrate that an intentionally inverted or failing assertion is detected and produces a failing result, then restore the probe and verify success. For validators and static architecture checks, use a valid input and an isolated invalid fixture or controlled violation to prove the expected pass and failure. Exercise fitness checks against their declared measurement and threshold where the required environment exists. If the full measurement depends on a future implementation, prove the available harness with a representative fixture and record the real measurement as pending. For manual-only checks, document the approved procedure, expected result and human verifier instead of claiming automated evidence.

Record the actual command and arguments, working directory, unit, target, check ID, level or type, mode, service dependencies and permission requirements with the tool version, fixture and observed results. Store non-secret evidence against the candidate revision in a durable checkpoint or phase PR. Distinguish missing discovery, unavailable services and harness errors from assertion failures. A missing required harness or failed proof blocks its dependent gate. Carry verified operations and service details forward for CI and the final environment record.

Check that each applicable strategy entry has an appropriate verified harness or a clearly identified human-only procedure. Review cross-unit boundaries, real versus substituted dependencies, supported targets and cleanup. Check the complete diff, exclude scratch and secrets, and preserve required assertions and modes.

Apply [Artifact Gates](../../../references/workflow-control.md#artifact-gates). Present the candidate, check-to-harness coverage, actual passing and intentional-failure evidence, limitations and intended publication. [Publish the Approved Candidate](../../../references/git-publication.md#publish-the-approved-candidate) on the scaffold branch and bind the evidence to its published revision. Follow the shared phase and session rules.
