# Release

Use for an explicitly requested release, release preparation or backport. Establish which local, commit, PR, merge, tag and artifact actions are authorized; a preparation request does not authorize all later publication. Reuse applicable authority rather than adding repeated confirmation gates. [Command Policy](command-policy.md) governs writes; [Exact Authorized Merge](branching-and-pr.md#6-exact-authorized-merge) governs agent merges.

## 1. Release Components

Follow the project's release contract. For the default SemVer/tag-based flow, these three components must agree; a generated changelog or platform release record may satisfy the project's documented alternative.

| Component     | Rule                                                                              | Source of Truth         |
| ------------- | --------------------------------------------------------------------------------- | ----------------------- |
| **Version**   | `<MAJOR>.<MINOR>.<PATCH>` per SemVer; bump derived from the changes (section 3)   | Tag                     |
| **Changelog** | An entry for the version, written for consumers and grouped by impact (section 4) | The project's changelog |
| **Tag**       | Annotated tag on the release commit; immutable once published (section 5)         | Git                     |

Tag, version and changelog must agree. When tags supply the runtime version, do not introduce duplicate stored values. When the project stores versions in files, update all required locations in the release-metadata change and verify them against the eventual tag.

## 2. Preconditions

Verify the selected remote and target branch: trunk for the normal flow, the maintained release line for a patch. Refresh when remote/ref access is authorized; without it, analysis may use explicitly dated cached evidence but release publication is blocked. Required verification/CI must pass for the intended release revision, and the release checkout must be clean with no unfinished operation. Preserve unrelated content elsewhere rather than cleaning it automatically. Identify the previous release tag using the project's tag naming convention. For example, use `git describe --tags --abbrev=0 <target-ref>` when all eligible tags are release tags; if the repository also uses non-release tags, select the appropriate previous tag for the intended release line explicitly; nearest reachable by ancestry is not necessarily the highest version or latest release date. If no prior tag exists, follow section 3 and ask the user for the starting version; do not assume a baseline. If current remote evidence, the target revision or required verification is unavailable, report the specific blocked publication stage; do not claim readiness.

## 3. Version Determination

Analyze `git log <last-tag>..<target-ref>` for the selected release line. [Semantic Versioning](https://semver.org/#semantic-versioning-specification-semver) defines version impact; commit types are evidence for that assessment, not a substitute for it:

| Change Signal / Impact                                                     | Default Handling for Projects Using SemVer and Conventional Commits                                                                                                                                                               |
| -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Confirmed breaking change (`!` in the header or `BREAKING CHANGE:` footer) | MAJOR for stable versions `1.0.0` and later, subject to the project's release policy                                                                                                                                              |
| `feat` with new backward-compatible functionality                          | MINOR for stable versions `1.0.0` and later                                                                                                                                                                                       |
| `fix` with a backward-compatible bug fix                                   | PATCH for stable versions `1.0.0` and later                                                                                                                                                                                       |
| Other types (`perf`, `security`, `refactor`, `build`, `docs`, etc.)        | Conventional Commits assigns no implicit SemVer bump to these types. Inspect the actual change and the project's release policy; classify consumer impact rather than treating the type alone as proof that no release is needed. |

Use commit headers as signals, not as a substitute for inspecting the changes. Select the highest applicable impact. If a change may be breaking but evidence is inconclusive, describe the uncertainty and ask the user before choosing a version. For `0.y.z` projects or custom/pre-release schemes, follow the project convention; if none is documented, propose a bump and obtain confirmation. If no tag exists, analyze the history and ask the user for the starting version. If the history does not follow Conventional Commits, inspect the changes and ask the user to confirm the proposed bump.

## 4. Changelog

| Item             | Rule                                                                                                                                                                                                |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Format           | Follow the project's existing changelog. If none exists, create `CHANGELOG.md` with the groups `Added` / `Changed` / `Deprecated` / `Removed` / `Fixed` / `Security`, newest version first          |
| Content          | Written for consumers, by impact; never a pasted commit log                                                                                                                                         |
| When to write    | Where the project maintains the changelog by hand: add the entry under `Unreleased` in the same PR as the consumer-facing change. At release time, rename `Unreleased` to the version with its date |
| Source           | The commit log is only input for drafting missing entries; edit by impact afterwards                                                                                                                |
| Breaking changes | Include migration instructions and the deprecation window the project planned                                                                                                                       |

## 5. Tag and Naming

| Item             | Rule                                                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Type             | Annotated: `git tag -a <tag> <sha> -m "Release <version>"`                                                                                                                                                                                                                                                                                                                                              |
| Format           | `v<MAJOR>.<MINOR>.<PATCH>` — always three components, even when `PATCH` is 0; follow the project's format if it already uses another                                                                                                                                                                                                                                                                    |
| Target           | The actual commit on the target branch that contains the final release version/changelog after merge (or the corresponding commit on the release branch for a patch release). Resolve the SHA after the PR merge method has completed; verify it is reachable from the target branch and that the release files match the tag. Do not tag the pre-merge PR head or assume the target is the branch tip. |
| Publish          | Push **exactly one tag**: `git push --no-follow-tags origin refs/tags/<tag>:refs/tags/<tag>`; inspect push configuration and never use `--tags`                                                                                                                                                                                                                                                         |
| Immutability     | A published tag is never moved or deleted                                                                                                                                                                                                                                                                                                                                                               |
| Version in files | If the project derives its version from the tag, edit no file. If it stores the version in files, update every location in the release commit so each value matches the tag                                                                                                                                                                                                                             |

**Naming for release-related objects:** For stable releases, `<version>` is the full `<MAJOR>.<MINOR>.<PATCH>` version without the leading `v`. A release maintenance branch identifies a version line, not a specific release version.

| Object                                            | Format                      | Example                 | Meaning                                                                                                                                       |
| ------------------------------------------------- | --------------------------- | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Stable version                                    | `<MAJOR>.<MINOR>.<PATCH>`   | `1.4.0`                 | Identifies one specific stable release.                                                                                                       |
| Git tag                                           | `v<version>`                | `v1.4.0`                | Identifies the released commit. A published tag is immutable.                                                                                 |
| Release PR branch (short-lived)                   | `chore/release-<version>`   | `chore/release-1.4.0`   | One branch per release-metadata PR. Targets trunk for a standard release or the corresponding release maintenance branch for a patch release. |
| Release commit and PR title                       | `chore(release): <version>` | `chore(release): 1.4.0` | The release-specific exception documented in `commit-convention.md`.                                                                          |
| Release maintenance branch (long-lived, optional) | `release/<MAJOR>.<MINOR>`   | `release/1.4`           | Maintains the corresponding version line, such as `1.4.x`, across multiple patch releases.                                                    |
| Patch release tag                                 | `v<version>`                | `v1.4.1`                | Identifies a specific patch release on the corresponding release maintenance branch.                                                          |

These are the default naming conventions for stable releases. If the project supports pre-release versions or uses a different versioning convention, follow the project's existing convention consistently across version files, branches, tags, commits, and release PRs.

## 6. Release Flow

1. Check preconditions; determine the proposed version and consumer-facing changes. Resolve actual version/policy ambiguity before dependent writes; do not reconfirm an unchanged approved version.
2. In an owned checkout create `chore/release-<version>` from the verified target branch, defaulting to trunk for a normal release. Prepare only the required changelog/version metadata. If release automation already owns these steps, follow that contract rather than duplicating them.
3. Verify the metadata change and commit when authorized using `chore(release): <version>` with a body explaining scope and reason. Push/open a PR to the actual target only within granted authority.
4. Wait for confirmed integration. A human may merge, or the agent may use the exact authorized merge route. Inspect platform evidence; no separate user confirmation is needed merely to observe a completed merge. If metadata changes are unnecessary under the project's release contract, verify the selected existing target commit directly.
5. Refresh and resolve the actual resulting target commit, accounting for squash/rebase/merge mapping. Verify reachability from the target branch, content/version/changelog agreement and required checks on the release candidate; do not assume the PR head survived or the current target tip is the right release.
6. When local tag creation is authorized, create `git tag -a <tag> <verified-target-sha> -m "Release <version>"`. Check `git rev-parse "<tag>^{commit}"` against that SHA and inspect the annotation. An existing conflicting tag is a blocker, not permission to move it; an exact matching tag can be reused after verification.
7. Publish exactly the selected tag ref only under R7 authority, then read its remote object/peeled target back. Local tag creation alone is not publication and does not authorize the push.
8. Artifacts, platform release records/notes and production exposure follow their own documented commands, verification and granted authority. Report prepared, tagged and published stages separately.

## 7. Release Maintenance Branch and Patch Release

| Item            | Rule                                                                                                                                                                                                                                                                                                                                                                                          |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| When            | Use only when the project maintains a supported release line or explicitly requires patching an older version while trunk has moved on. Do not create a release maintenance branch automatically for every release.                                                                                                                                                                           |
| Create          | `release/<MAJOR>.<MINOR>` from the exact released tag or commit (for example, `release/1.4` from `v1.4.0`). A human creates and pushes the maintenance branch; the agent prepares the commands.                                                                                                                                                                                               |
| Fix source      | Implement and test the fix on a normal `fix/<description>` branch from trunk, then merge it into trunk through a PR. After that, create a distinct, unused backport branch such as `fix/<description>-release-<MAJOR>.<MINOR>` from the release maintenance branch, run `git cherry-pick -x <sha>` for the verified trunk fix commit, and open a PR targeting the release maintenance branch. |
| Merge direction | Trunk → release branch by cherry-pick only. A release branch is never merged back into trunk                                                                                                                                                                                                                                                                                                  |
| Direct commits  | No direct commits or pushes to shared trunk/release branches. Prepare the backport and release-metadata commits on short-lived branches and merge them by PR                                                                                                                                                                                                                                  |
| Tag             | After the backport PR and the release-metadata PR have both been merged, create the next patch tag (for example `v1.4.1`) on the verified post-merge commit, per section 5                                                                                                                                                                                                                    |
| Changelog       | Update the patch entry to the released version on the release branch. Reflect the released patch on trunk through a separate PR/new commit according to project policy, never by reverse-cherry-picking the release branch                                                                                                                                                                    |
| Lifecycle       | A human deletes the branch when releases are no longer made from it                                                                                                                                                                                                                                                                                                                           |

### Patch-Release Sequence

1. Prepare the fix on trunk through the normal topic/PR flow and verify its resulting integrated trunk commit. Agent merge requires exact authority; otherwise wait for confirmed human integration.
2. Create a distinct backport branch from `release/<MAJOR>.<MINOR>`. Inspect the actual integrated fix diff before `git cherry-pick -x <sha>`: a squash commit may include unrelated work, and a merge commit needs an understood mainline parent (`-m <parent>`). Select only the intended fix and required dependencies; resolve ambiguity rather than copying a whole PR blindly. Verify the result on the older release line, then push/open its PR when authorized.
3. After the backport PR is confirmed merged, fetch and confirm the fix is present on the release branch.
4. Create `chore/release-<version>` from the updated release branch. Update the release branch's changelog entry and any version-storing files, verify and commit `chore(release): <version>` with a meaningful body, then push and open a second PR targeting the release branch when those actions are authorized.
5. After the release-metadata PR is confirmed merged, fetch and verify the actual post-merge release-branch commit contains the fix, version, and changelog. When R7 authority covers it, create the annotated tag on that SHA and push exactly that tag ref. Never tag the pre-merge PR head.
6. When in the requested scope, reflect the patch release in trunk through a separate PR/new commit following the project's changelog/version policy. Do not reverse-cherry-pick the release branch into trunk.
