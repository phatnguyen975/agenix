# Axis: dependencies

## Purpose

Verify that dependency, tool, plugin, and vendored-code changes are necessary, trustworthy, compatible, and reproducible.

## Method

1. Determine the installation boundary: use the workspace root when a parent workspace owns the package and dependency graph; otherwise use the nearest project root owning both its manifest and lockfile. Treat nested independent projects separately.
2. Compare dependency manifests and lockfile diffs. Identify direct, transitive, optional, development, build, and runtime dependency changes.
3. Review each added dependency and each material upgrade using the checks below.
4. Read release notes/changelogs and migration guidance for upgrades; do not infer risk from semantic-version labels alone.
5. Verify package-manager identity, lockfile integrity, reproducible installation, scripts, provenance, license, and vulnerability information using project-pinned tool versions and official documentation.
6. Use actual build/test results supplied by the main agent; do not run installers or project scripts in this sub-agent.

## Checklist

### New Dependency

- Does the existing platform, standard library, or an already-approved dependency provide the capability?
- Is the dependency justified by the current change and proportionate in size, maintenance burden, and transitive dependency count?
- Is it actively maintained with credible ownership, release history, issue handling, and security response?
- Are known advisories relevant to the selected version and reachable usage? Are transitive vulnerabilities included?
- Is its license compatible with project and distribution obligations?
- Is provenance trustworthy? Consider package/repository identity, publisher/ownership changes, typosquatting/lookalikes, suspicious release timing, compromised accounts, and unverifiable artifacts.

### Upgrade or Removal

- Were release notes, breaking changes, deprecations, and migration steps reviewed?
- Is the upgrade set a coherent, reviewable unit? Are unrelated risky major upgrades isolated where that improves diagnosis and rollback?
- Are runtime/build/test behavior and platform/version constraints checked against the upgraded version?
- Were transitive changes reviewed rather than looking only at the top-level package?
- Does removal eliminate obsolete code/config and avoid leaving unused transitive packages?

### Installation Boundary and Lockfile

- Do declared package-manager name/version, lockfile, CI, and project documentation agree? Report ambiguous or conflicting signals rather than guessing.
- Is there one authoritative lockfile per dependency graph/workspace boundary, according to the package manager and project policy?
- Is the lockfile generated by the package manager, committed, and reviewed as part of the change rather than hand-edited?
- Do manifests and lockfiles agree, and does CI use the project's documented frozen/immutable install mode?
- Are registry/source overrides, git dependencies, URL dependencies, and integrity hashes intentional and trustworthy?

### Install-time and Build-time Execution

- Are lifecycle/install scripts, native build steps, code generators, plugins, and build extensions identified before executing untrusted package code?
- Where supported, are install scripts disabled by default or governed by a narrow, version-aware approval policy?
- Are required scripts reviewed and approved explicitly, and do clean frozen installs succeed under the committed policy?
- Are build steps isolated with least privilege and no unnecessary production credentials?
- Are package-manager behaviors checked against the project's pinned version and current official documentation?

### Vulnerability and Provenance Management

- Are known advisories triaged by version, affected code path, reachability, exploitability, and exposure?
- Do deferrals include rationale, owner, compensating controls, and review date?
- Is forced/automatic remediation reviewed as a code change, including version and lockfile diffs?
- Where supported and required, are registry signatures, provenance attestations, checksums, SBOMs, and artifact attestations verified?
- Are dependency policies/scanners applied consistently without treating every advisory as exploitable or every missing scanner as a finding absent a project requirement?

## Severity Guidance

- Confirmed malicious/lookalike dependency, exploitable reachable vulnerability, or install-time execution with an unsafe trust boundary — Critical or High.
- Unreviewed risky major upgrade, untrusted source, or materially inconsistent lockfile/install policy — High or Medium.
- Unnecessary dependency, unmaintained package with practical risk, or unresolved license concern — Medium.
- Minor dependency hygiene with no material impact — Low.

## Boundaries

- Vulnerabilities in first-party code belong to security.
- Build-pipeline identity and execution-boundary flaws belong to security; package provenance/lockfile/install-script review belongs here.
- Architectural dependency direction belongs to design.
- Do not prescribe commands from another package manager or a different pinned version.
