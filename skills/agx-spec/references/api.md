# Define Feature Interfaces

## Applicability and Inputs

Use this step when the feature introduces, consumes or changes a consumer-visible interface. Include owned APIs and messages, external integrations, and applicable package or CLI interfaces. If none apply, report the basis for omission without creating an artifact.

Read the approved feature record and behavior specification on the feature specification branch, including acceptance, business rules and interaction boundaries. Verify scaffold merge and required checks on the refreshed default branch. Apply [Decide Readiness and Record Progress](../../../references/work-items-and-evidence.md#decide-readiness-and-record-progress) to feature dependencies and applicable overrides; use [Local Tracker](../../../references/trackers/local.md#read-verify-and-update) for local status verification and the applicable shared rules for Git-owned feature evidence in remote modes. A blocked feature requires an explicitly scoped human override before permitted work can proceed.

Read the applicable approved system or client design, tech stack, conventions and test strategy for interface ownership, protocols, constraints and validation tooling. Inspect existing contracts and relevant ADRs when affected. For an external interface, obtain its authoritative definition and version or revision. Follow applicable scoped project instructions.

Resolve conflicts with approved behavior or architecture through the owning amendment route before relying on changed decisions. Ask the human about material unresolved interface choices; do not invent provider guarantees or business rules.

## Design and Validate Contracts

1. Map each applicable interaction to its consumers, provider, trust boundary and the feature behavior it supports. Identify whether the interface is owned, externally owned or already covered by an existing definition. Keep package or CLI behavior in `spec.md` when it adequately describes the public interface; do not force it into a wire-contract format.
2. For a new or materially changed supported owned API or message contract, use [API Contract Design](../../api-contract-design/SKILL.md) as the main workflow. Reuse approved protocol and format choices; selectively load its protocol, contract and concern references. Apply its compatibility guidance to affected existing interactions and obtain approval for breaking changes before applying them. For an unchanged external contract, pin its authoritative source and edition or revision and record relevant consumer expectations and gaps without editing the provider's definition.
3. Place owned shared definitions, schemas and wire examples under `docs/contracts/`, following the approved project organization. When establishing or materially changing the layout, propose a structure and trade-offs for human confirmation before writing dependent files. For OpenAPI, consider a single document for a small, manageable surface and a referenced multi-file layout when size, ownership or maintenance warrants it; preserve a coherent entry point and compatible tooling. Reuse an approved layout unless a material change is needed. Keep one editable source for each definition; treat bundles and exports as derived outputs. Create or update `docs/contracts/README.md` with the approved layout, contract entry points and applicable verified commands for validation, linting, viewing or mocks. Reference the existing command source rather than duplicating its configuration; omit unavailable operations.
4. Use compatible fragments from the capability's assets only where useful. Define applicable operations, schemas, security, errors and interaction semantics at their owning locations; reference business rules rather than duplicating them. Create `docs/features/<feature-id>/api-contract.md` only for material semantics the canonical definitions cannot adequately express, linking the relevant contracts and rules. Record external pins and any public interface details in the appropriate feature artifact so downstream consumers can find them.
5. Identify conformance cases linked to feature acceptance and affected operations or messages, including relevant success and error cases. Carry these into implementation using the approved test strategy; exercise the real boundary when available. Reuse canonical valid wire examples for consumers and mocks; label deliberately invalid data as test fixtures. Do not claim implementation or real integration has passed future checks.

Run applicable validation and lint commands established by the approved toolchain, including definition, reference, schema and example checks where supported. Apply the capability's relevant verification checklist and assess compatibility against the prior approved contract, using an available approved comparison check where applicable. Report exactly what ran and any gaps; parsing alone does not establish specification conformance. Resolve material gaps before approval. Implementation-level API and conformance tests are performed when the corresponding implementation is available.

## Approve and Publish

Apply [Artifact Gates](../../../references/workflow-control.md#artifact-gates). Present contract paths or external pins, the confirmed organization, consumer impact and compatibility, acceptance and conformance coverage, checks and limitations, remaining applicable specification work and intended publication. Bind the applicable contract entry points and residual API artifact in the feature record as described in the skill entry point; include the contract README when it exists. Identify the feature's relevant operations or messages in the specification or residual API artifact, linking directly to stable contract locations where supported. Do not invent anchors or duplicate contract definitions. Include any necessary approved documentation map updates in the same candidate.

[Publish the Approved Candidate](../../../references/git-publication.md#publish-the-approved-candidate) on the feature specification branch and bind approval and verification evidence to its revision in the phase PR or a durable checkpoint. Reconcile existing work on resume. If this is the final applicable specification step, verify the complete specification set and its applicable evidence, then obtain separate merge authority and verify the merge and required checks. Otherwise leave the phase open for the remaining applicable steps. Follow the shared session closure rules.
