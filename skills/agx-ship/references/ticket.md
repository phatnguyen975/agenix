# Deliver the Ticket

## Inputs and Resume

Resolve the ticket and its feature from the merged delivery plan on the refreshed default branch. Verify the selected tracker mapping, approved ticket and task definitions, ownership, dependencies, current contracts, candidate branch, review decision and actual check evidence. Read applicable scoped instructions, test strategy, `environment.agenix.json`, feature exposure boundary and the ticket's durable checkpoints. Select the existing ticket branch and implementation PR using [Establish the Branch and Pull Request](../../../references/git-publication.md#establish-the-branch-and-pull-request); do not create a second PR on resume.

Apply [Decide Readiness and Record Progress](../../../references/work-items-and-evidence.md#decide-readiness-and-record-progress), [Specify Verification and Assess Evidence](../../../references/work-items-and-evidence.md#specify-verification-and-assess-evidence) and the configured [Local](../../../references/trackers/local.md#read-verify-and-update), [GitHub](../../../references/trackers/github.md#confirm-state-and-closure) or [Jira](../../../references/trackers/jira.md#confirm-native-state) rules. In local mode use `verify-status.py` with the applicable inputs from the tracker guide; in remote modes verify native ticket and child records and Git evidence at their sources. Read the existing PR, head, base, review, checks and merge state before retrying any publication or merge. Reuse valid decisions and verified writes.

## Check and Publish the Candidate

1. Revalidate ticket acceptance, approved task definitions and evidence, dependencies, current review and exact candidate. Confirm required local checks and human judgments, and the isolation that makes merging safe before whole-feature acceptance. Bind review to the candidate using [Bind Review and CI to the Candidate](../../../references/git-publication.md#bind-review-and-ci-to-the-candidate). A substantive change invalidates affected review and requires the appropriate build or review route; explicitly approved bookkeeping may carry evidence forward only after checking the complete diff. Identify required checks that can run only after PR publication as pending.
2. For local tracking, prepare prospective ticket `DONE` and task completion metadata only for obligations awaiting final-head CI. Embed applicable checkpoints in the ticket or task record using the [Checkpoint Schema](../../../templates/evidence/checkpoint.schema.json). Include the exact pending evidence and approved bookkeeping in the candidate; prospective state does not establish verified completion. For remote tracking, retain native nonterminal state until its completion conditions are verified. Preserve all existing task definitions, results and evidence.
3. Apply [Artifact Gates](../../../references/workflow-control.md#artifact-gates). Present the candidate, review and local evidence, remaining PR checks, prospective state and exact publication actions. After approval, [publish the candidate](../../../references/git-publication.md#publish-the-approved-candidate), create or update the ticket implementation PR and attach or reference durable review and check evidence. Keep native ticket references non-closing. Verify the PR points to the intended branch, base and head; do not claim CI passed before it runs.

## Verify Merge Readiness and Closure

Verify required final-head checks, actual native reviews and the approved head using [Bind Review and CI to the Candidate](../../../references/git-publication.md#bind-review-and-ci-to-the-candidate). Reconcile tasks waiting for PR-dependent results; under the stated publication approval close eligible native tasks and read back their actual state. Require every assigned task to have verified completion or an approved cancellation, and ensure the applicable delivery set and acceptance remain covered. In local mode evaluate prospective state with `verify-status.py` using `candidate-ci` and the actual PR/check inputs. Check candidate validity, dependencies and PR checks separately: a required pending, failed or unavailable check blocks merge. For prospective `DONE`, `completion: pending` is expected before merge and does not by itself block an otherwise ready candidate; verified completion is established after merge.

Apply [Merge the Approved Head](../../../references/git-publication.md#merge-the-approved-head): present the exact PR and head for a separate human merge decision. The human may merge or authorize AI to merge; verify protections, native approvals and required checks, and do not bypass them or enable auto-merge. Queue submission is pending merge. If the human merges later, stop with the PR and remaining action and resume this same invocation after revalidation.

Apply [Verify Delivery and Recover from a Failed Check](../../../references/git-publication.md#verify-delivery-and-recover-from-a-failed-check). Confirm actual merge and required post-merge results on the refreshed default branch, including squash mapping. In local mode verify the approved ticket state reached that branch and evaluate delivery using the tracker guide. In GitHub or Jira mode, close the native ticket under the stated publication approval only after verification, then read back label and native closure state. Record reviewed head, merge SHA, actual checks and closure in a durable PR or tracker comment using the [Checkpoint Template](../../../templates/evidence/checkpoint.md). Record only facts available at that time; do not require a post-merge commit to the merged ticket record solely for this evidence.

If a required post-merge check fails, retain the original failure and leave the ticket incomplete. Route repair through a new linked ticket without making it depend on closure of the original; resume only after that repair merges and required checks covering the failed scope pass on the repaired revision. In local mode include the repair in the merged feature plan and set its `origin-ref` to the original ticket path or PR URL so the verifier can discover it. Record both PRs, revisions and results in durable PR evidence. If an unmerged candidate needs substantive fixes, retain the PR, report the blocker and suggest the owning build or review step; revalidate before reuse. Follow the shared cleanup and session closure rules.
