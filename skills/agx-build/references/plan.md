# Plan Ticket Tasks

## Inputs and Readiness

Resolve the ticket from the feature's merged delivery plan on the refreshed default branch. Verify its approved definition, native mapping where applicable, ownership, dependencies, feature specification and plan merge with required checks. Read the ticket's pinned references and acceptance, applicable contracts and UI/data impacts, scoped project instructions, conventions, test strategy, `environment.agenix.json` and relevant existing code and harnesses. Inspect existing task definitions and evidence on the owned branch or tracker before allocating IDs or adding work.

Apply [Decide Readiness and Record Progress](../../../references/work-items-and-evidence.md#decide-readiness-and-record-progress) and the configured [Local](../../../references/trackers/local.md#read-verify-and-update), [GitHub](../../../references/trackers/github.md#create-and-read-issues) or [Jira](../../../references/trackers/jira.md#create-and-read-issues) tracker rules. Use merged evidence for ticket prerequisites. A blocked ticket requires an explicitly scoped human override before permitted work can proceed. Resolve material scope or authority conflicts before dependent planning.

## Refine the Approved Ticket

Use [Work Breakdown Planning](../../work-breakdown-planning/SKILL.md) in `Recursive` mode within the ticket's approved boundary. Use its slice quality bar, scope assessment, dependency and cycle checks; render the result in the owning records, not its standalone template. Refine until executable leaves have coherent outcomes and concrete verification. If a leaf remains coarse or a material decision is unresolved, report the obstacle and do not present that leaf as execution-ready. Preserve the ticket's scope and cover every selected acceptance obligation and applicable quality requirement.

For each task, specify an observable outcome, sibling dependencies, task-local acceptance IDs and criteria. Each criterion's `covers` identifies one or more acceptance IDs selected by the ticket. Inherit the ticket's pinned scope; add a narrower pinned reference only when needed. Assign stable IDs after existing allocations, including cancelled work. Reconcile all existing approved definitions and checkpoints on resume. Additional obligations get new IDs and an origin; do not rewrite approved tasks or dependencies silently.

When planning review fixes, read the durable review decision and findings from the ticket checkpoint or tracker. Map each approved fix to an existing unfinished task when its approved scope covers the work. For a new obligation or a fix covered only by a `DONE` or `CANCELLED` task, create a new sibling task with an origin reference to the finding and preserve the prior task and evidence. Keep the ticket `IN-REVIEW`; confirm the new plan before execution.

Apply [Specify Verification and Assess Evidence](../../../references/work-items-and-evidence.md#specify-verification-and-assess-evidence). Select the method per task, not per ticket: `test-first` by default; propose `test-after` or `manual` only with a concrete task-specific reason and obtain human approval as part of the plan gate. A ticket may contain all three. Select distinct applicable approved check IDs from the environment and test strategy; automated methods need at least one. For manual tasks record the procedure, expected result and responsible human, and include applicable automated checks. Manual tasks are leaves and cannot be prerequisites.

Confirm the selected harnesses, commands, targets, services and evidence are available. A predecessor must have sufficient locally verifiable evidence to unblock a dependent task in the same run. If it depends solely on a PR-only result, resolve the breakdown or prerequisite before approval without weakening the check. Use [Test Design Techniques](../../tdd/references/test-design-techniques.md) selectively to derive missing cases from approved behavior, regardless of the selected method; do not impose a test-first cycle on other methods.

## Approve and Publish the Plan

Prepare each task's ID, title, outcome, dependencies, acceptance, verification and initial `READY` or `BLOCKED` status, with origin or precise references only when applicable. Keep execution results and completion evidence for later. Check coverage, IDs, acyclic dependencies, method-specific requirements, check references and harness readiness.

- **Local:** append the approved tasks to the existing ticket's `tasks` array using the [local ticket schema](../../../templates/records/local-ticket.schema.json). Preserve existing definitions and evidence. Run the installed [artifact validator](../../../scripts/validate-artifacts.py) with `--project-root <absolute-project-root> --stage task-plan --item <ticket-id>` before publication.
- **GitHub or Jira:** draft tasks using [Native Task](../../../templates/records/native-task.md) and [Remote Tracker Records](../../../references/work-items-and-evidence.md#remote-tracker-records). Render GitHub sub-issues or Jira sub-tasks under the verified existing parent; preserve the parent definition. After approval, record the exact approved task-plan snapshot in a parent comment before creating children. Use the configured tracker guide to create or reconcile children, verify native parentage, labels, status and supported dependency links, then record verified mappings in the parent. Preserve drafts until reconciled; never repeat an uncertain create without checking existing results.

Apply [Artifact Gates](../../../references/workflow-control.md#artifact-gates) to the exact task set, dependencies, acceptance coverage, methods, exception reasons, manual judgments and intended writes. Approval covers the stated publication. After approval, commit and push the local plan on the owned ticket branch, or perform the approved remote snapshot and child writes. Bind approval and actual results to the ticket checkpoint; verify publication and mappings. Report blockers and pending work. Do not begin implementation automatically; follow the shared session closure rules.
