# Agenix Implementation Plan

> **Status:** Approved\
> **Updated:** 2026-11-17\
> **Design:** [Agenix proposal](agenix-proposal.md)\
> **Scope:** Phase 3 setup and Phase 4 implementation; detailed skill content is authored in Phase 4.

The [proposal](agenix-proposal.md#1-scope-and-design-principles) owns workflow behavior; this plan selects how to build it. Read Section 1 for inventory, Sections 2–3 for reuse and routing, Sections 4–6 for implementation choices, and Sections 7–9 for execution and acceptance. The proposal takes precedence if the two conflict; a design change requires a human-approved amendment before dependent implementation.

## 1. Complete Skill Inventory

The target inventory has **43 skills**: 20 existing capabilities retained, one newly authored capability, ten required workflow skills and twelve upstream web capabilities, each with explicit applicability. An inventory entry does not mean its implementation is already compatible with Agenix. `Adapt` means a bounded, reusable correction before integration; `Reuse` still requires validation of instructions, resources and applicability. Changes to the approved selections require an explicit plan decision.

Existing skills remain available even when not routed by Agenix.

### 2.2 Existing Coverage That Should Be Preserved

- `domain-modeling` already separates focused/full scope and permits proportionate modeling. Reuse its selective references and domain template, stripping only inapplicable detail through legitimate template guidance.
- `evolutionary-architecture-design` supports focused decisions, technology trade-offs, ADR supersession and planned versus active fitness functions. Use focused client design for frontend-only; never force its complete system template there.
- `codebase-design` already distinguishes source structure from runtime/domain/contracts and permits material decisions to reuse prior approval. Its design, conventions and test-layout references cover structure work without a new scaffold skill.
- `database-design` covers relational/document initial models and explicitly excludes other stores. For client key-value or specialized persistence, `agx-architect data` uses a concise project-specific model and official selected-store documentation; do not pretend the SQL/document skill covers it. Later impact analysis needs an established compatible baseline or a reviewed model extension first.
- `api-contract-design` supports multiple protocols and project-selected layout. Reuse relevant assets only for compatible interfaces. CLI/package public contracts remain in the behavior/public-interface references; no new CLI-API skill is justified.
- `codegraph-intelligence` supplies conditional structural analysis when CodeGraph is selected and ready. Check index freshness and candidate/worktree identity, distinguish heuristic edges from observed behavior and preserve ordinary source/text tools for their own tasks. Adapt unconditional tool preference, automatic setup and interface fallback to caller-selected prerequisites; its generic capability stays independent of Agenix.
- All capabilities receive a focused correctness/style/resource-route check before reuse. In particular, version claims in API/security/database guides must be checked against official sources and the chosen target, not copied as universal current defaults.

## 3. Workflow-to-Capability Mapping

`R` = required method for substantive work in the applicable step; `C` = invoke only when the stated condition applies; `O` = optional aid for a concrete opportunity. These labels govern loading a capability, not whether a required output/check can be skipped. Read/verify unchanged approved inputs without regenerating them or reinvoking their authoring method.

The step reference owns orchestration, scope, paths, gates and status. Capability invocation supplies a bounded method: exact input sections, relevant mode/reference, expected contribution and return point. A capability must not start another workflow step. Direct instructions are sufficient for deterministic configuration, record management, command execution and publication; no capability is required merely to fill a mapping cell.

### 4.3 Template Placement and Reuse

1. Reuse a suitable capability template at its original resource path, whether upstream puts it in `assets/` or `references/`. Do not copy it into root `templates/` just for uniformity.
